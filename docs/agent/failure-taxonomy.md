# Failure Taxonomy

この文書は、CodeEval実験で発生する失敗をどのように分類するかを定義する。

## 目的

CodeEvalでは、単に「失敗」と記録するだけでは不十分である。

失敗がどの段階で起きたのかを分けて記録することで、原因を分析しやすくする。

特に、v3とv4の比較では、以下の違いを区別することが重要である。

- 設計文書生成が失敗したのか
- C++コード生成が失敗したのか
- コンパイルで失敗したのか
- テストで失敗したのか

## 基本方針

失敗は、可能な限り次のカテゴリに分類する。

## 1. pipeline_failed

実験パイプライン自体が正常に動作しなかった状態。

### 例

- コマンドライン引数が不正
- 入力ファイルが存在しない
- データセットのメタデータが不足している
- スクリプトがクラッシュした
- 想定外のディレクトリ構造になっている
- 実験制御側でタイムアウトした

### 解釈

これは、ローカルLLMの設計理解能力やコード生成能力を直接示す失敗ではない。

まず実験基盤やスクリプトを確認する必要がある。

## 2. design_generation_failed

ローカルLLMが、利用可能な設計文書を生成できなかった状態。

### 例

- 設計文書が空
- 対象関数と関係ない説明が出力された
- 出力が途中で切れている
- 必要な設計情報がほとんど含まれていない
- 設計文書の形式が大きく崩れている

### 解釈

設計生成プロンプト、またはモデルのソースコード理解能力に問題がある可能性がある。

v3では、特に重要な失敗カテゴリである。

## 3. code_generation_failed

設計文書から、利用可能なC++コードを生成できなかった状態。

### 例

- C++コードが出力されていない
- Markdownの説明だけが出力された
- コードではなく自然言語の説明が出力された
- 別のプログラミング言語で出力された
- 必要な関数が存在しない
- 関数シグネチャが大きく異なる

### 解釈

コード生成プロンプトに問題がある可能性がある。

v4では、コード生成時のself-checkによってこの失敗が減るかどうかを見る。

## 4. compile_failed

C++コードは生成されたが、コンパイルに失敗した状態。

### 例

- 構文エラー
- include不足
- namespaceの誤り
- 関数シグネチャの誤り
- 未定義変数
- 戻り値の型の不一致

### 解釈

生成コードが、構造的に不正であることを示す。

v4でこのカテゴリが減少した場合、コード生成self-checkが有効だった可能性がある。

## 5. test_failed

生成コードはコンパイルできたが、テストに失敗した状態。

### 例

- アルゴリズムが誤っている
- エッジケースに対応できていない
- 出力値が間違っている
- 部分的な実装になっている
- 問題制約を誤解している

### 解釈

コードは実行可能だが、意味的に正しくない状態である。

この場合、設計文書に必要な振る舞いが不足していた可能性、またはコード生成モデルが設計文書を正しく使えなかった可能性がある。

## 6. passed

生成コードがコンパイルされ、用意されたテストを通過した状態。

### 解釈

その試行では、設計生成からコード生成、テスト通過までの流れが成功したとみなす。

## 重要な区別

`compile_failed` と `test_failed` は必ず分ける。

`compile_failed` は、生成コードを意味的に評価する前に失敗している。

`test_failed` は、生成コードは実行可能だが、振る舞いが誤っている。

この2つを混ぜると、プロンプト改善の原因分析が難しくなる。

## 記録ルール

実験結果をまとめるときは、可能な限り次の情報を残す。

- 最終ステータス
- 失敗した段階
- モデル名
- プロンプトバージョン
- 対象問題
- 実行コマンド
- 代表的なエラー内容

## 手動修正禁止ルール

失敗を成功に見せるために、生成された設計文書やC++コードを手動修正してはいけない。

壊れた生成物は壊れたまま記録する。

改善する場合は、生成物そのものではなく、プロンプト、スクリプト、実験条件を別途修正する。
